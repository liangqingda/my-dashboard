# 抽帧探针的生命周期（`useFrameProbe`）

进度条悬停预览靠一支 1px 隐藏 `<video>` 按需 seek 取帧（见 `../use-video-frames/README.md`）。
这支探针什么时候挂地址、换片时怎么断流，都收在这里——它同时管着主视频与探针两支元素。

## 为什么地址要晚一步

打开一条视频时，主视频要先把元数据与首帧解出来。如果探针在同一刻也挂上地址，同一个文件会被
两支 `<video>` 各读一路：首帧解码、首段缓冲正在吃盘，第二条流把带宽与磁盘分走，观感就是
「这条片子加载变慢了」——连翻几条时更明显，因为每翻一条都会再起两路，旧的不一定马上收。

所以探针在主画面就绪（`ready`）之后再等 `PROBE_ARM_DELAY`（600ms）才挂地址：

- 打开的那一段只有一条流在读盘；
- 连翻几条时，中间被翻过去的片子探针**根本没挂过**，一条数据都没抽；
- 代价是刚打开、探针还没挂的那几百毫秒里，进度条 hover 先回落到数字浮标（探针还没有元数据，
  `ready` 为 false）。

反过来，**真有人等帧时不必等**：进度条 hover 会让调用方先调 `arm()`，主画面一就绪就立刻挂地址。
这一档空档是给「只是打开看一眼」的片子省盘的，不该罚在等帧的人身上——
否则 hover 恰好落在空档里，浮出与换帧两道计时都因探针未就绪空跑，指针不动就再也等不到。

## 为什么只取元数据

挂上后探针用 `preload="metadata"`：它要的是「按位置 seek 到某一秒」，不是顺序播。
真正要哪一帧时浏览器再按 `Range` 拉那一段——本地取一次几十毫秒，慢的从来是解码不是传输
（口径同 `../use-video-frames/README.md` 的实测）。这样播放期间也不会多一条整份流。

## 卸载即断流

换片是调用方用 `key` 重挂（一个视频一个实例），元素会被移除，但浏览器收掉在途的 `Range`
请求还要等一轮。这里在卸载时对两支元素都做 `pause` + 清 `src` + `load()`，请求当场结束：

- 连续翻篇时旧请求不会再占着连接与读盘，新片子的元数据不用排在它们后面；
- 外接盘上的片子也不会因为「还有流挂着」卡住推出。

**断流要延后到微任务再判活着的标记**：StrictMode 在开发模式下对每个 effect 走
「挂载 → 卸载 → 再挂载」，两次在同一个 tick 里同步发生。直接在同一次 cleanup 里断流，
会把刚起来的这条流掐掉——表现为开发模式下打开视频一直停在「正在读取视频…」。
所以卸载先把 `liveRef` 置 false 并排一个微任务，微任务里 `liveRef` 又变回 true 就说明只是
模拟卸载，什么都不做；真卸载时没人再置回来，这才真的断。

## 边界

- 只负责挂地址与断流，不抽帧、不排队（那是 `use-video-frames` 的事）。
- `probeSrc` 没到点时给的是**空串**，调用方必须挂 `undefined`：`<video src="">` 会被浏览器
  当成当前页地址去请求。
