# use-image-zoom-pan

`FreeImage` 的放大 / 缩小与平移：捏合改倍率、两指滑动平移，两件事都走同一族 `wheel` 事件，
最终落到同一份「倍率 + 位移」。

## 输入通道

| 手势 | 浏览器报什么 | 这里怎么接 |
| --- | --- | --- |
| 触控板捏合（Chromium / Firefox） | 带 `ctrlKey` 的 `wheel` | 原生 `wheel` 监听、`passive: false`；改倍率 |
| 触控板捏合（Safari） | `gesturestart` / `gesturechange` | 同一份原生监听，按手势起点倍率 × `event.scale` 算 |
| `Ctrl` + 滚轮 | 带 `ctrlKey` 的 `wheel` | 与捏合同一条路径 |
| 触控板两指滑动 / 鼠标滚轮 | **不带** `ctrlKey` 的 `wheel`（`deltaX` / `deltaY` 两轴都有） | 平移画面（仅放大后） |

捏合与滑动必须先 `preventDefault`：不拦的话浏览器处理的是**整页**（缩放 / 滚动），画面本身不动。

## 锁了什么

- **倍率 1–5**：1 就停，不缩到「整图装下」以下（再小只是画面缩在中间一圈黑边里）；
- **锚点缩放**：以指针位置为锚点，锚点下的像素缩放前后停在原地，手指在哪捏就从哪展开；
- **位移夹取**：位移上限 = `(画出来的尺寸 × 倍率 − 舞台尺寸) / 2`，所以放大时滑不出黑边，
  缩回 1 倍时自动回正（1 倍时上限为 0）。「画出来的尺寸」是 `object-fit: contain` 之后画面实际占的那块，
  不是图片盒子——整屏时盒子被撑到视口，按盒子算就会多出一截能拖出去的黑边；
- **平移只在放大后**：1 倍时没有可移的余地，`wheel` 原样放行，不做无意义的拦截；
- **平移方向反着滚动**：往下滚动看到图片下半部分，与滚一块大图的直觉一致；
- **滚动量按像素算**：Firefox 的鼠标滚轮报的是行（`deltaMode === 1`），先按 `WHEEL_LINE_HEIGHT`
  换成像素，否则平移和缩放都几乎不动；
- 加载中、读不出来、`interactive={false}`（裁剪这类要按布局尺寸量的状态）时 `enabled: false`：
  捏合照样拦掉整页缩放，只是不改倍率；滚动也不平移，免得挪动一块空舞台 / 一张正在选框的图；
- **关掉缩放先 `reset()`**：回到 1 倍、位移清零。裁剪选框量的是未缩放的布局尺寸，若留在放大态，
  选框会和实际编码出来的像素错位；
- **图片节点可以让外部持有**（`imageRef`）：裁剪要把同一张 `<img>` 交给 canvas 编码，舞台不传就
  自己建一个，传了就用外部那个——两边必须指向同一节点，否则量出来的比例对不上。舞台节点由
  `FreeImage` 的 callback ref 同时写给自己与外部（`stageRef`），叠加层用外部那一份。

## 为什么不做指针拖拽

macOS 的三指拖拽是系统辅助功能，要先在「系统设置 → 辅助功能 → 指针控制」里打开；浏览器也拿不到
触控板的原始触点数。而两指滑动本来就是浏览器稳定上报的 `wheel`——同一套事件里既分得出捏合
（`ctrlKey`），也分得出滑动（无 `ctrlKey`），不需要第二套手势通道，也就省掉了「拖完那一下 click
要不要吞掉」这类配套逻辑。

## 为什么状态放这里

`FreeImage` 由调用方用 `key` 换实例，换图即重置倍率；状态若提到调用方，就得多写一个
「换图要复位」的 effect，还要把 transform 逐层传下去。
