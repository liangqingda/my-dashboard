# 规范文档怎么写：规则在前，例子只作注脚

适用于 `docs/`、入口 `AGENTS.md`、组件 / hook 目录的 `README.md`。

## 判据

一条规则要能**删掉所有例子后独立执行**：把例子里的组件名、文件名、字段名、数字划掉，剩下的话
仍能告诉读者「什么情况算什么、该落到哪」。做不到，说明写的是案例汇编，不是规则。

## 三种合法写法

| 类型 | 怎么写 | 例子处在什么位置 |
| --- | --- | --- |
| 规则 | 先给判据：问什么、怎么答、落哪 | 规则之后，标「示例：」；示例不参与判定，可替换 |
| 登记表（资产清单） | 表头写明名单来源（脚本 / 目录 / 单一数据源） | 清单本身是事实，不靠它反推判据 |
| 契约（一次具体集成） | 命令、输入输出、错误口径、失败时怎么办 | 事实即内容，具体路径可以直列 |

## 不许的写法

- 用「现有 X 是形态 1 的典型例子 / 边缘案例」逐个裁决，来定义类别边界；
- 用目录快照、组件清单、事故复盘（「真实发生过」「早先就是」「以前会…」）承担规则；
- 用夹具文件名 + 具体计数当口径（某测试文档「计数 1 / 2」），夹具一改规则就读不出来；
- 把「反例（曾被 review 点名）」当补充规则；反例确有必要时，只附在判据后一行；
- 在 `docs/` 里重复组件规格：规格写组件目录 `README.md`，`docs/` 只放跨文件判据与索引。

## 改文档时的四条检查

1. **删例子**：把示例整段去掉，规则句是否还完整；
2. **换名词**：规则句里的每个专有名词，换成一个新对象是否仍成立；
3. **查来源**：清单 / 快照有没有写明来源；没有来源的清单等于把现状当规则，改成脚本校验或直接删；
4. **grep 提示**（只作线索）：`例：|例如|典型|早先|以前|曾被|真实发生过` 命中后按上面三条判，
   该保留的示例统一写成「示例：…」。

## 落位

新增 `docs/` 文件必须同时加进 `AGENTS.md` 索引表（`scripts/check-structure.mjs` 校验）；单主题
细则只在本文件，跨主题约束才进「硬约束速览」。
